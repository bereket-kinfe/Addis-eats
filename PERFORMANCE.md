# Performance notes

## Menu filter work

The search input waits 250 ms after the last keystroke before updating the filtered menu. A burst of eight keystrokes inside that debounce window therefore causes one filter update instead of eight: an 87.5% reduction in filter updates for that burst. Filtering is memoized and the catalog is loaded in a server component, rather than imported into the client page bundle.

## Reproduce the client bundle measurement

After `npm run build`, inspect the JavaScript chunk references for `/menu` in `.next/server/app/menu/page_client-reference-manifest.js`, then total those files under `.next/static` (optionally gzip each with Node's `node:zlib`). Compare the resulting total to the baseline below. Chunk names are generated by Next.js and change between builds.

Baseline captured from the build before these six-area changes:

| Menu route JavaScript | Raw bytes | Gzip bytes |
| --- | ---: | ---: |
| Shared route chunk | 25,285 | 7,491 |
| Menu-specific chunk | 4,124 | 1,619 |
| **Total** | **29,409** | **9,110** |

Measured from the production build after the changes:

| Menu route JavaScript | Raw bytes | Gzip bytes |
| --- | ---: | ---: |
| Shared route chunk | 11,122 | 4,360 |
| Menu-specific chunk | 3,745 | 1,433 |
| **Total** | **14,867** | **5,793** |

That is 49.4% fewer raw bytes and 36.4% fewer gzip bytes in the menu route's application entry chunks. This comparison covers the route's `app/layout` and `/menu` entry chunks listed in the client-reference manifest, not every framework/runtime script. Menu data is now sent as server-rendered page data instead of being embedded in the page's JavaScript.
